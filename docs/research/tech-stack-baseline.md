# Tech stack & architecture baseline — research findings

Resolves Wayfinder ticket [#6](https://github.com/Lucy-yunn/test/issues/6). Feeds DRAFT ADR
[`docs/adr/0001-architecture-baseline.md`](../adr/0001-architecture-baseline.md).

Scope: lock the v1 technical baseline for the used auto-parts marketplace MVP — Next.js usage
pattern, database + ORM, auth approach, image storage, i18n library, hosting target. The
**detailed** domain schema, permission matrix, order state machine and messaging model are owned
by sibling tickets (#2, #3, #4, #5, #8, #10, #11, #12); this ticket only fixes the engine each
of those will be built on.

Primary sources: the Next.js docs **bundled with the installed package** at
`node_modules/next/dist/docs/` (this is a modified/newer Next.js — see warning in `AGENTS.md`).
File paths below are relative to that directory. Package version: `next@16.3.4`, `react@19.2.8`
(from `package.json`).

## 1. This is Next.js 16.3.4 — what actually changed vs. training-data Next.js

`AGENTS.md` warns that APIs, conventions and file structure may differ from what a model was
trained on. The bundled upgrade guide (`01-app/02-guides/upgrading/version-16.md`) and the
current reference pages confirm the following breaking changes. Every one of these is a place
where naive code-generation from memory will be wrong.

### 1.1 Async Request APIs are now fully async (no sync fallback)
`cookies()`, `headers()`, `draftMode()`, and `params` / `searchParams` in `page`/`layout`/
`route`/`default` are **Promises**. The Next.js 15 synchronous compatibility shim is **removed**.
You must `await` them (or `React.use()` them in Client Components).
Source: `01-app/02-guides/upgrading/version-16.md` ("Async Request APIs (Breaking change)").

```tsx
export default async function Page(props: PageProps<'/listings/[id]'>) {
  const { id } = await props.params
}
```

Typed helpers `PageProps`, `LayoutProps`, `RouteContext` are globally available and generated by
`next dev` / `next build` / `next typegen`.
Source: `01-app/03-api-reference/03-file-conventions/route.md` (Route Context Helper);
`internationalization.md` (uses `PageProps<'/[lang]'>`).

### 1.2 `middleware.ts` → `proxy.ts` (renamed + runtime change)
The `middleware` file convention and named export are **deprecated** and renamed to `proxy`.
The `proxy` runtime is **Node.js only and not configurable**; the `edge` runtime is **not
supported** in `proxy` (stay on `middleware` if you truly need edge — deferred by Next).
Config flags renamed too, e.g. `skipMiddlewareUrlNormalize` → `skipProxyUrlNormalize`.
Source: `01-app/02-guides/upgrading/version-16.md` ("`middleware` to `proxy`");
`01-app/03-api-reference/03-file-conventions/proxy.md`.

Impact for us: locale detection/redirect and optimistic auth redirects live in `proxy.ts`, and
they run on Node — our auth/session libs don't need edge compatibility.

### 1.3 Turbopack is the default bundler for `dev` and `build`
No `--turbopack` flag needed. A **custom `webpack` config makes `next build` fail** unless you
pass `--webpack`. `turbopack` is now a top-level key in `next.config` (was
`experimental.turbopack`). Turbopack filesystem caching is on by default.
Source: `01-app/02-guides/upgrading/version-16.md` ("Turbopack by default").

Impact: do not add a `webpack` function to `next.config.ts`; do not install webpack loaders/
plugins. Our current `next.config.ts` is empty — keep it minimal.

### 1.4 `next lint` removed
`next lint` is **gone**; `next build` no longer runs ESLint. Use the ESLint CLI (or Biome)
directly. `@next/eslint-plugin-next` now defaults to **flat config**. The `eslint` key in
`next.config` is removed.
Source: `01-app/02-guides/upgrading/version-16.md` ("`next lint` Command", "ESLint Flat Config").

Impact: the scaffold already has `"lint": "eslint"` and `eslint.config.mjs` (flat) — correct.
CI must run lint/type-check as explicit steps.

### 1.5 `next/image` — several breaking default changes
Source: `01-app/02-guides/upgrading/version-16.md` ("`next/image` changes"); `01-app/01-getting-started/12-images.md`; `01-app/03-api-reference/02-components/image.md`.

- `images.domains` is **deprecated** — use `images.remotePatterns` (protocol/hostname/pathname).
- `images.qualities` default is now **`[75]` only**; other `quality` props are coerced to the nearest allowed value. Declare `qualities` if you need more.
- `images.minimumCacheTTL` default `60s` → **`14400s` (4h)**.
- `16` removed from default `images.imageSizes`.
- Local images with query strings require `images.localPatterns[].search`.
- Optimizing images from local/private IPs is blocked unless `images.dangerouslyAllowLocalIP`.
- `images.maximumRedirects` default is now `3` (was unlimited).
- `next/legacy/image` is deprecated.
- The default optimizer **does not forward auth headers** when fetching `src`; for
  authenticated sources use `unoptimized` or a custom `loader`.

Impact: whatever bucket/CDN host we pick for listing photos must be added to `remotePatterns`.

### 1.6 Caching / PPR model changed — do **not** turn on Cache Components for v1
`experimental.dynamicIO`, `experimental.useCache`, `experimental.ppr` and the route-segment
`experimental_ppr` are **removed**. PPR-style behaviour is now opt-in via the top-level
`cacheComponents: true`, and it "is not a rename-only change: it can surface build errors for
uncached data outside of `<Suspense>` and requires adopting the Cache Components model."
`cacheLife` / `cacheTag` are stable (drop the `unstable_` prefix). `revalidateTag` now **requires
a second `cacheLife`-profile argument**; new `updateTag` (read-your-writes) and `refresh`
(refresh client router from a Server Action) live in `next/cache`.
Source: `01-app/02-guides/upgrading/version-16.md` ("Partial Prerendering (PPR)", "Caching APIs",
"`experimental.dynamicIO` and `experimental.useCache`"); `01-app/01-getting-started/08-caching.md`.

Impact: v1 stays on the **"previous"/default caching model** (documented in
`01-app/02-guides/caching-without-cache-components.md`) — request-time dynamic rendering by
default, `<Suspense>` + `loading.tsx` for streaming. Cache Components is a later optimisation, not
a baseline decision.

### 1.7 Other removals / changes that bite
- **Node.js 20.9+** required (Node 18 dropped); **TypeScript 5.1+**; browser floor raised
  (Chrome/Edge/Firefox 111+, Safari 16.4+). Source: version-16.md ("Node.js runtime and browser support").
- `serverRuntimeConfig` / `publicRuntimeConfig` (`next/config`) **removed** — use env vars;
  wrap runtime `process.env` reads after `await connection()` to keep them out of the build.
  Source: version-16.md ("Runtime Configuration").
- **Parallel routes now require an explicit `default.js`** in every slot or the build fails.
  Source: version-16.md ("Parallel Routes `default.js` requirement").
- `next dev` and `next build` use separate output dirs (`.next/dev`) and a lockfile prevents two
  dev servers. `next build` output no longer prints `size` / `First Load JS`.
  Source: version-16.md ("Concurrent `dev` and `build`", "Performance Improvements").
- React **19.2** canary in the App Router; **React Compiler** support is stable but **off by
  default** (needs Babel, slows builds). Source: version-16.md ("React 19.2", "React Compiler Support").
- `opengraph-image` / `icon` / `sitemap` generating functions now receive `params` / `id` as
  Promises. Source: version-16.md.
- AMP support fully removed. `unstable_rootParams` → `next/root-params`.

### 1.8 Agent-file mechanics (leave the tree clean)
`next dev` writes/re-adds the `<!-- BEGIN:nextjs-agent-rules -->` block in `AGENTS.md` via
`node_modules/next/dist/server/lib/generate-agent-files.js`. Do not fight it in diffs; do not run
`next dev` in a research ticket. Source: `AGENTS.md`; version-16.md ("Set up AI agent docs").

## 2. Recommended Next.js usage pattern for v1

Source for the patterns: `01-app/01-getting-started/05-server-and-client-components.md`,
`07-mutating-data.md`, `15-route-handlers.md`, `02-guides/authentication.md`,
`02-guides/internationalization.md`.

- **App Router**, everything nested under **`app/[locale]/…`** so `locale` is a root param
  (`next/root-params`) available to every server component and server-side helper without prop
  drilling. `generateStaticParams` enumerates `['en']` for now (`['en','bg']` later).
- **Server Components by default** for all reads: the funnel search, Part/Listing pages, seller
  center dashboards, admin lists. Data is fetched in a **Data Access Layer** (`app/lib/dal.ts`)
  that calls `verifySession()` first, memoised with React `cache()`, returning DTOs (never raw
  rows). This is the pattern the bundled auth guide prescribes.
- **Client Components** only for genuine interactivity: funnel dropdowns, favorite toggle,
  message composer, image gallery, language switcher, admin status-change controls.
- **Server Functions / Server Actions** for **all mutations**: buyer registration, login/logout,
  favorite/unfavorite, send message, place order (stub), and every staff admin action
  (create/edit Listing, advance/cancel Order). Each action re-checks auth+role internally —
  "Server Functions are reachable via direct POST requests, not just through your application's
  UI" (`07-mutating-data.md`). Use `useActionState` for pending/validation UI; `revalidatePath`
  / `updateTag` / `redirect` after writes.
- **Route Handlers** kept to a minimum — none are required for the MVP UI. Reserve `app/api/**`
  for: a health check, and later webhooks (payments) / a mobile-or-partner API. Note a
  `route.js` cannot sit at the same segment as `page.js`.
- **Rendering strategy**: request-time dynamic rendering for anything behind auth or reading the
  DB; `<Suspense>` + `loading.tsx` for streaming; static generation only for marketing/legal
  pages. Do **not** enable `cacheComponents` or `reactCompiler` for v1.
- **`proxy.ts`** (Node runtime): locale resolution/redirect + optimistic (cookie-only) auth
  redirects. Real authorization always happens in the DAL / action, close to the data.
- Keep `next.config.ts` minimal; the only near-term additions are `images.remotePatterns` (photo
  host) and `i18n`-library wiring.

## 3. Database + ORM

### Recommendation: PostgreSQL + Prisma (managed Postgres, e.g. Neon or Supabase)

**Why Postgres.** The domain is squarely relational: `Category → Part → Listing`, `Vehicle`,
a many-to-many `Fitment` (Part ↔ Vehicle, manually verified), `Provenance` (1:1 on Listing),
`Seller`/`Location`, `Order` (single-item, state machine), `MessageThread`/`Message`,
`Favorite`. Postgres also gives us, for free, the things the roadmap will want: `jsonb` for
open-ended technical attributes on Part, `enum` types (condition, order status, role), array/GIN
and `pg_trgm` full-text for search beyond the funnel, and it is the default target of every
managed host and every Next.js example. It does not block multi-country, more sellers, or real
payments later.

**Why Prisma.** For a solo builder working with Claude Code, Prisma optimises for the thing that
matters — iteration speed with a coding assistant: the largest volume of training data and
worked examples, a single declarative `schema.prisma` that Claude can edit safely, first-class
migrations (`prisma migrate dev`), a typed client that surfaces schema drift as compile errors,
and `prisma db seed` for the required demo seed data. It works cleanly from Server Components and
Server Actions (the bundled auth guide's examples are ORM-style `db.insert(...).returning(...)`).

**Serverless caveat (matters if we host on Vercel):** Prisma over many short-lived serverless
invocations needs pooled connections — use Neon's pooled endpoint / Supabase's pgBouncer, or
Prisma Accelerate. A long-running Node server (Railway/Render/Fly) avoids this entirely.

### Genuine either/or for the founder: Prisma vs Drizzle
`Drizzle` is the credible alternative: SQL-first, thinner runtime, faster cold starts, no
generate step. It trades away some of Prisma's assistant-friendliness and migration ergonomics.
The bundled auth guide's code samples actually read like Drizzle (`db.query.users.findMany`,
`eq(...)`). Either is fine and reversible early; **default recommendation is Prisma** for pace.

> The concrete tables/columns/enums are **not** decided here — they belong to #2 (core domain
> model), #3 (taxonomy), #4 (vehicle data), #5 (part identity), #8 (listing), #10 (orders),
> #11 (messaging). This ADR only fixes "Postgres + one TS ORM".

## 4. Auth approach (roles: buyer / seller / staff-admin)

Per the map: **buyers self-register** with email + password (Q16); **sellers are
staff-provisioned** — white-glove onboarding, no self-serve seller signup in v1 (Q4);
**staff/admin** accounts are provisioned manually (Q2, a shared back-office for founder +
boyfriend). Google / Facebook buttons are **rendered but inert** ("coming soon") in v1 (Q21).

The bundled auth guide (`01-app/02-guides/authentication.md`) lays out the mechanics we must
follow regardless of library: Server-Action sign-up/login with Zod validation and password
hashing (bcrypt/argon2), an HttpOnly + Secure + SameSite session cookie, a `verifySession()`
DAL used by every read/action, optimistic checks only in `proxy.ts`, and **auth checks pushed
close to the data, not into layouts** (layouts don't re-render on navigation). Its "Auth
Libraries" list includes Auth.js/NextAuth, Better Auth, Clerk, Supabase, Lucia-style DIY, etc.

### Recommendation: Auth.js (NextAuth v5) — Credentials provider + Prisma adapter, JWT sessions
- Maximum training data / worked App-Router examples → fastest with Claude Code.
- `auth()` helper works in Server Components, Server Actions, Route Handlers, and `proxy.ts`
  (Node runtime — fine under v16's `proxy` constraint).
- Credentials provider covers email+password now; Google/Facebook are a few lines to enable
  later (button stays disabled in v1).
- Role: a `role` enum column (`BUYER | SELLER | STAFF`) on `User`, surfaced in the session
  token and checked in the DAL. Seller & staff accounts are created by a staff-only admin action
  that sends a set-password link; buyers self-register.

### Genuine either/or for the founder: Auth.js vs Better Auth
**Better Auth** is the modern alternative and is arguably a better *fit*: email+password and
sessions are first-class (no Credentials-provider/JWT-only awkwardness), it ships an
admin/role/organization plugin that maps neatly onto buyer/seller/staff + "staff creates seller",
and social providers are trivial to add later. Cost: less training data, so more doc-reading for
the assistant. **Default recommendation: Auth.js for pace; switch to Better Auth if the role /
provisioning logic in #12 turns out heavy.** Either keeps password hashing + DB-backed users and
does not block social login later.

> The full permission matrix, seller-provisioning flow, and session lifetime are **#12's** call.
> This ticket fixes "library + email/password + role-on-user + DAL pattern".

## 5. Image / photo storage (listings require photos)

Constraints: staff upload multiple photos per Listing; MVP is a seeded demo; must render through
`next/image`; low ops.

**Do not** commit photos to `public/` — a redeploy/rebuild is the source of truth and user
uploads don't belong in the repo or the build. Use an **S3-compatible object store** and render
with `next/image` + an `images.remotePatterns` entry for the bucket host (remember v16's
`qualities: [75]` default and 4h `minimumCacheTTL`).

### Recommendation: pick the store that matches the DB host
- **If Postgres = Supabase → use Supabase Storage.** One vendor, one dashboard, one set of
  credentials, signed URLs, works from Server Actions. Lowest ops for a solo builder.
- **Otherwise → UploadThing** (built specifically for Next.js App Router, typed upload helpers,
  generous free tier, fastest to wire) **or Cloudflare R2** (S3 API, zero egress fees, cheapest
  at scale) if you want to stay vendor-neutral.

All three are reversible: the app only stores an object key / URL per photo. Keep an
`images.remotePatterns` allow-list and a thin `lib/storage.ts` wrapper so the provider is a
one-file swap.

## 6. i18n library (English v1, Bulgarian later, EUR only)

Source: `01-app/02-guides/internationalization.md`. Next.js gives the **routing** primitive
(`app/[locale]/…` + `proxy.ts` locale detection + `generateStaticParams`) but not localisation
itself. Its "Resources" list: `next-intl`, `next-international`, `next-i18n-router`,
`paraglide-next`, `lingui`, `tolgee`, `next-intlayer`, `gt-next`, plus a zero-dependency
"dictionary" pattern (JSON per locale + `getDictionary(locale)` behind `import 'server-only'`).

### Recommendation: next-intl
- Most widely used, App-Router-native, Server-Component-first (message catalogs stay server-side
  — no client bundle cost, per the docs' note about the DIY approach).
- ICU messages (plurals/interpolation) and **built-in number/date/currency formatting** — we
  need consistent EUR formatting from day one.
- Ships the `[locale]` segment + `<Link>` / locale-switcher patterns, so the "language toggle
  from the start" requirement is a small, well-trodden task.
- Adding `bg` later = add `messages/bg.json` + one entry to the locales array.

### Alternative: the built-in dictionary pattern (zero deps)
Viable precisely because v1 is one language with a toggle. Cost: you build the switcher,
fallbacks and currency formatting (`Intl.NumberFormat`) yourself. Lower magic, slightly more
boilerplate. `next-international` is the middle ground (type-safe, tiny). **Default: next-intl.**

Either way: structure all UI strings as message keys from the first screen — retrofitting
hard-coded English later is the expensive path the map is trying to avoid.

## 7. Hosting target

Source: `01-app/01-getting-started/17-deploying.md`, `02-guides/self-hosting.md`. v16 supports
Node server, Docker (`output: 'standalone'`), static export (too limited for us), and the
Adapter API. **Verified adapters: Vercel and Bun.** `next/image` optimisation and `proxy` both
work self-hosted under `next start` with zero config.

### Recommendation: Vercel for v1 + managed Postgres with pooling (Neon)
- Zero-config, first-party/verified adapter, preview deploys per branch (useful for the
  boyfriend's review loop, Q2), lowest ops burden for a solo builder — which is the explicit
  optimisation target.
- Nothing about Vercel blocks the roadmap (multi-country, more sellers, real payments).
- Caveats to design around, not blockers: serverless functions need **pooled DB connections**
  (use Neon pooled endpoint / Prisma Accelerate); keep the app **portable** — standard Node
  server semantics, `output: 'standalone'` build works, no Vercel-only APIs — so a later move is
  cheap.

### Genuine either/or for the founder: Vercel vs a plain Node host (Railway / Render / Fly.io)
A long-running Node container is a simpler mental model (no cold starts, ordinary DB pooling,
predictable flat pricing, trivial Dockerfile via `standalone`) and avoids serverless-Prisma
friction, at the cost of a bit more setup and no built-in preview URLs. **Default: Vercel** for
speed now; Railway/Render is the fallback if serverless constraints or pricing bite.

## 8. Supporting choices (low-risk, stated for completeness)

- **Package manager:** pnpm.
- **Language:** TypeScript `strict`. Run `next typegen` in CI for typed routes/props.
- **Styling:** Tailwind CSS v4 — already in the scaffold (`@tailwindcss/postcss`), keep it.
- **Validation:** Zod (used throughout the bundled auth guide) — shared schemas for forms +
  Server Actions.
- **Lint:** ESLint flat config via the CLI (`next lint` is gone). Type-check + lint as explicit
  CI steps since `next build` runs neither.
- **Testing (light for MVP):** Vitest for units + Playwright for the funnel→order happy path;
  both have bundled guides (`02-guides/testing/`).
- **Runtime:** Node 20.9+ (v16 minimum).
- **Config:** env vars only (`serverRuntimeConfig`/`publicRuntimeConfig` are removed); read
  runtime values after `await connection()`.

## 9. One-line stack

Next.js 16 App Router (Server Components + Server Actions, `app/[locale]`, `proxy.ts`, default
caching) · PostgreSQL + Prisma on managed Postgres (Neon/Supabase) · Auth.js v5 email+password
with a `role` enum and a `verifySession()` DAL · object-storage photos (Supabase Storage /
UploadThing / R2) via `next/image` + `remotePatterns` · **next-intl** with `app/[locale]` ·
hosted on Vercel · Tailwind v4 · Zod · pnpm.

## 10. Decisions the founder must make (carried into the ADR)

1. **ORM:** Prisma (recommended, fastest with Claude Code) vs Drizzle (lighter, SQL-first).
2. **Auth library:** Auth.js/NextAuth v5 (recommended, most examples) vs Better Auth (better
   role/provisioning fit, fewer examples).
3. **Hosting + DB host:** Vercel + Neon (recommended, lowest ops, serverless pooling caveat) vs
   Railway/Render/Fly + bundled Postgres (simpler runtime model, more setup). This choice also
   picks the photo store (Supabase Storage if Supabase; else UploadThing/R2).
4. **i18n:** next-intl (recommended) vs zero-dep dictionary pattern vs next-international.
